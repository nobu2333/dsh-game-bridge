# 迁移建议：把 dsh-game-core 复用到另一个本地项目

> 2026-10-29 记录。**本文只是建议，不涉及任何具体项目的代码改动**。
> 背景：引擎最初从另一个本地项目的抓屏/OCR 经验提炼而来；这里讨论「将来它是否要
> 反向被复用」，以及三种做法的取舍。

## 现状

两条独立代码线：

| | 宿项目（未公开） | dsh-game-core（本仓库，MIT） |
|:--|:--|:--|
| 定位 | 本地陪伴 / 双环对话 / 桌面形象 / 长期记忆 | 只做「眼睛 + 手 + 小脑」的本地引擎 |
| 抓屏 | 自己有 DXcam 实现 | 本引擎实现 + 多显示器映射 |
| OCR | 自己有 RapidOCR 封装，含实测调优 | 本引擎同款调优（注释里标注了出处与原因） |
| 帧差分 | 自己有 | 本引擎的 `grab_diff`（分类 + 指标） |
| 窗口/输入 | 自己有 | 本引擎的 Windows 解析 + 安全闸/审批/审计 |
| 测试 | 大量既有单测 | 46 个引擎单测 |

**当前选择：不迁移（选项 A）**。引擎是插件专用的独立实现；两边共享的是「实测结论」
而不是代码依赖——这条边界让宿项目不必为插件的发布节奏负责。

## 三个选项

### A. 不迁移（现状，推荐先保持）

- 优点：零风险；两边可以各自演进，插件版本不绑架宿项目；
- 代价：抓屏/OCR/窗口是**两份实现**；实测调优常数（OCR 的 `max`、DXcam 单次 grab、
  COM 清理）要在两边同步，漏了就在某一边退化；
- 缓解：调优常数写成两边注释 + 本文档引用；新功能优先做进 `dsh-game-core`。

### B. 宿项目反向依赖 `dsh-game-core`（发布并稳定后考虑）

前提：本包已在 PyPI 发布、版本 ≥ 0.1、连续两个版本没改公开 API。

- 宿项目依赖 PyPI 包（MIT 兼容），只替换**观测/输入底座**：
  抓屏、OCR、窗口解析、输入通道；
- 保留不动：陪伴逻辑（对话、记忆、人设、形象、语音）、UI、配置格式；
- 需要一个**适配层**把引擎返回的 dict 映射回宿项目现有数据类型（避免大面积改 API）；
- 收益：Win32/OCR/多显示器只维护一份；缺陷修复两边同时受益；
- 风险：宿项目的延迟预算按「进程内调用」定，而引擎是 stdio 子进程——`snapshot`
  往返会多 ~5–10ms。对低频采样无影响，但**不能塞进 <100ms 的反射链路**；
  反射链路（语音打断等）继续留在宿项目进程内。

### C. 反过来：插件包住宿项目

**否决**。宿项目含有用户数据、资产许可与个人迭代史，不能作为公开依赖；
也会把插件的版本节奏绑死在一个不发布的仓库上。

## 如果将来做 B：步骤

1. `dsh-game-core` 发到 PyPI，锁定版本；
2. 在宿项目加适配层，先替换 OCR（最容易对拍，输出形状简单）；
3. 用宿项目已有的标定/回放工具对拍两版 OCR 结果与耗时；
4. 再替换抓屏/窗口（注意构造参数与 `grab()` 语义差异）；
5. 全量测试必须全绿；跑一局实机确认延迟预算没被击穿；
6. 观察 2 周再删旧实现（保留 git 历史即可回滚）。

## 不该迁移的

陪伴逻辑（对话/记忆/人设/形象/语音）、UI、配置与游戏档案格式。
它们依赖玩家本机数据，插件化只会让两边都变难。

## 边界提醒

- 引擎**不允许**依赖任何具体宿主项目的模块；反过来也建议成立，避免循环依赖；
- 本项目自己的「两条铁律」（随时夺回 / 反作弊不接）必须在代码里成立，不能假定对方实现了；
  「无人不自娱」是宿项目自己的规则，dsh-game-bridge 已于 2026-10-30 移除，复用方不应依赖它；
- 许可证：两边都是 MIT 时才能自由互借；若任一方改许可，B 方案需重评。
