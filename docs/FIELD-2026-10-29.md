## 3. P0：装不上 / 看不见 / 开不起来

### P0-1 安装矩阵缺失：桌面版与 web profile 是两套

**现象**：按 README 执行 `dsh plugin --profile web add dsh-game-bridge` 后，新会话里没有
`game_*` 工具。

**证据**：
- `~/.dsh/profiles/web/package.json`：dependencies 与 `dsh.profile.bundles` 都有 `dsh-game-bridge`；
- 宿主进程命令行：`... app.asar\dsh C:\Users\<user>\.dsh\profiles\desktop ...`（端口 13659/14815 的监听者就是它）；
- `~/.dsh/profiles/desktop/package.json` 原本 dependencies 为空、bundles 只有 5 个官方 bundle；
- CLI 拒绝管理 desktop：`dsh plugin --profile desktop version-exemptions` →
  `error: profile "desktop" is managed exclusively by the Electron application`；
  `dsh --profile desktop --dump-config` 同样被拒。
- 应用内才有插件管理（asar 内含 `dsh-host-plugin-inventory` / `dsh-client-ui-settings-plugins`），
  由它安装后才写进 desktop profile。

**根因**：profile = 一套独立的插件树；Electron 桌面版固定跑 `desktop`，而 README/CLI 的
安装路径指向 `web`。两者不共享插件。

**建议**：
1. README 增加「安装矩阵」：桌面 App / `dsh web` / `dsh headless` 分别怎么装、装完必须重启宿主；
2. 对 `dsh plugin` 的 desktop 拒绝文案补上替代路径（「请在应用设置→插件中安装」）；
3. 插件自身可在启动时打印「已加载的 profile 名与 package 路径」，便于用户自证装对了没有。

### P0-2 安装产物指向临时路径，重启即可能失效

**现象**：desktop profile 的依赖是 `file:<local-output>\dsh-game-bridge-0.0.1.tgz`
（本地打包产物放在仓库 `tmp/` 下，而 `tmp/` 在 `.gitignore` 里）。

**风险**：该 tgz 被清理/移动后，下次启动插件加载失败（且报错发生在启动阶段，用户不知所措）。

**建议**：安装器把 tarball 复制进 profile 存储目录（或强制 registry/github 来源并在 boot 时
校验路径存在，失败时输出可行动提示）。

### P0-3 后端在宿主启动时定死，运行期没有任何开关

**证据**：
- `lib/index.js:158`：`const backend = env.DSH_GAME_BRIDGE_CONTROL || 'dry-run'`（模块加载时读）；
- `engine/session.py:53`：`self.backend = control_backend or os.environ.get(...)`（引擎进程启动时读）。

**后果**：默认 dry-run 一旦启动就改不了；想用真实后端必须「设 env + 完全重启宿主」。
对非技术用户几乎不可发现（`game_status` 只显示 `backend: dry-run`，没有「怎么切」）。

**建议**：把后端做成插件配置项（cordis config schema）或 `game_backend` 工具（切换时走审批），
至少在 `game_selftest` / `game_status` 文案里写清「设置 `DSH_GAME_BRIDGE_CONTROL=vgamepad` 并重启」。

### P0-4 审批策略 `never` 会让真实后端 fail-closed，且报文不可行动

**证据**：本部署的权限预设 `danger-full-access` 是 `approval: never`；DSH `dsh-user-approval`
的 `NEVER_SENTENCE` 明确写「actions that require approval are rejected automatically」；
插件 `controlApprovalHook` 对非 dry-run 的 `game_attach` 返回 `kind:"ask"`。

**后果**：用户即便设对了 env，attach 仍会被自动拒绝；而拒绝信息不会告诉他去改预设。

**建议**：attach 失败时输出具体指引（「当前审批策略=never；请在权限预设里切到 ask，或让部署方
提供审批应答者」）；文档给出「桌面版 + ask 预设」的推荐组合。

### P0-5 vgamepad 后端开箱即坏（缺依赖 + 自检误导 + venv 无 pip）

**证据**：
- `engine/pyproject.toml` dependencies 只有 `numpy / dxcam / rapidocr-onnxruntime`，**没有 vgamepad**，
  也没有 optional-dependencies；
- `lib/bootstrap.js:168` 安装 spec 是 `dsh-game-core==0.0.1`，不带 extra；
- 引擎 venv（uv 创建）**没有 pip**、也没有 vgamepad：`import vgamepad` → `ModuleNotFoundError`；
- 而 `game_selftest` 返回 `engine: ready (cache)`，`game_controls` 仍然列出 12 个手柄按钮；
- 本次是靠从另一个 venv 复制 `vgamepad 0.1.0`（自带 ViGEmClient.dll）才跑起来的。

**后果**：用户设 `DSH_GAME_BRIDGE_CONTROL=vgamepad` → attach 成功 → 第一次 `game_act` 抛
`ModuleNotFoundError`，错误信息还被引擎 stderr 尾巴淹没。

**建议**：
1. `pyproject.toml` 加 `[project.optional-dependencies] gamepad = ["vgamepad>=0.1.0"]`；
2. bootstrap 按 `DSH_GAME_BRIDGE_CONTROL` 选 extra（或在首次切到真实后端时补装）；
3. `game_selftest` 增加「所选后端的依赖是否可用 / 虚拟手柄能否创建 / XInput 槽位」；
4. attach 阶段做一次 backend 预检（创建再销毁），失败 fail-fast 并给出安装提示；
5. venv 没有 pip 要在文档写清：`uv pip install --python <venv>\Scripts\python.exe vgamepad`。

## 4. P1：输入到底到没到游戏

### P1-1 没有前台/焦点管理，且 act 静默成功

**证据**：
- 仓库 `lib/` 与 `engine/` 全量搜索 `SetForegroundWindow` / `GetForegroundWindow`：**0 命中**；
- `DESIGN.md:19` 架构图里写了「窗口焦点 / 输入法看护」，实现里没有；
- 实测：Cuphead 窗口在 962×567 位置时，DSH 窗口覆盖同区域，`snapshot` 抓到的是 DSH 界面；
- `act` 的返回只有 `{action, safety, attached, actions_total}`，没有「游戏是否前台/是否收到」。

**后果**：XInput 只送前台窗口；用户切回聊天窗口后，agent 的 `game_act` 全部「成功但无效」，
审计日志也记录成正常动作。这是最难排查的一类失败。

**建议**：
1. act/plan 前校验 `GetForegroundWindow() == attached.hwnd`，不匹配则拒绝（fail-closed）并返回
   `foreground: {hwnd, title}`；或提供显式 `game_focus`（需审批）；
2. `game_attach` 返回 `foreground` 状态；
3. 动作结果里带 `delivered_to_foreground: bool`。

### P1-2 抓屏是整屏裁剪，遮挡时静默拍错人

**证据**：
- `engine/capture.py`：DXcam 抓整块显示器；`engine/snapshot()` 里按窗口矩形裁剪；
- 实测截图 `<local-output>\game-bridge\frames\snap-1793279702185.png`（94KB）内容为 DSH 聊天
  窗口，而 session 是 attach 在 Cuphead 上的，**没有任何警告**；
- `DESIGN.md:74` 标题写「窗口级抓屏（不是整屏）」，与实现不符（实现是整屏抓+裁剪）。

**后果**：agent 会基于错误画面做决策并注入；对「看一眼就判断」的玩法是灾难级。
这也是最值得优先修的可观测性问题。

**建议**：
1. 优先换真正的窗口抓屏：`PrintWindow(PW_RENDERFULLCONTENT)` 或 Windows Graphics Capture；
2. 低成本兜底：snapshot 同时返回 `foreground`（hwnd/title）、`occluded` 估算（attached 窗口是否
   被其它窗口覆盖/是否前台），并在 `game_snapshot` 文本里显著标注；
3. 文档把「整屏裁剪」的限制写进已知限制，别让人以为是窗口抓屏。

### P1-3 虚拟手柄落到 XInput slot 1（玩家 2），菜单无反应

**证据**：
- 会话期 XInput 探针：`slot 0: none`、`slot 1: CONNECTED buttons=0x0000`；按住 A 时
  `slot 1: CONNECTED buttons=0x1000`（XUSB_GAMEPAD_A）→ 注入本身是好的；
- 同一台机器「新进程创建 pad」探针：`before-create: []` → `after-create: [0]` → 退出后 `[]`；
- PnP：`USB\VID_045E&PID_028E\01 / 02 / 03` 三个「Xbox 360 手柄」节点（会话时一个 OK、两个
  Unknown 幽灵节点）；
- 主菜单 OCR 前后逐字一致，两次 `A`（各 120ms）零反应；屏幕右下角提示仍是键盘的 `CONFIRM Z`。

**假设**（未证实）：手柄在 slot 1 = 玩家 2，Cuphead 主菜单只接受 1P（slot 0）输入；
或引擎长生命周期进程中 pad 创建时机/幽灵节点导致槽位漂移。

**建议**：
1. 创建 pad 后立刻用 `XInputGetState` 扫 0–3，记录槽位；不是 0 就销毁重建（或报错）；
2. 把槽位写进 `game_attach`/`game_status` 的返回与工具文本；
3. 引擎退出时清理设备节点（避免累积幽灵手柄）；
4. 文档写清「虚拟手柄槽位 = 玩家序号」的含义。

### P1-4 热插拔未验证

本次是游戏启动后（21:08）才在 21:11 创建虚拟手柄。Unity/Rewired 通常支持热插拔，但没有证据。
需要在真人在场时做对照：**先建手柄再启动游戏** vs 反过来。

## 5. P2：效率、安全闸、工程卫生

### P2-1 单步步进太贵，模型往返是主成本

只读实测（引擎本机）：

| 操作 | 耗时 |
|:--|:--|
| `attach`（含抓屏预热） | **884 ms** |
| 第 1 次 `snapshot`（OCR 冷启动） | **2234 ms** |
| 后续 `snapshot`（带 OCR） | **378–389 ms** |
| `snapshot`（不带 OCR） | 36 ms |
| `events`（帧差） | 11 ms |
| `windows` | 2 ms |
| `status`（含 tasklist 反作弊扫描） | 484 ms |

再叠加模型每次工具调用 3–5s：进 Cuphead 一个关卡要菜单 4–6 步 → 30–60s，旁观体验很差。

**建议**：
1. `game_macro` / `act_sequence`：一次工具调用在引擎侧执行一串 `(hold/tap/wait)`，
   把「移动+射击+跳」这种组合一次发完；
2. `game_plan` 支持多键同时按住（现在只支持单键，实际游戏几乎都需要组合键）；
3. 「按 OCR 文本选择/点击」的原语（菜单导航专用），能显著减少往返。

### P2-2 `game_plan` 是盲闭环

`advance` 只看帧差分的静/动决定侧移，不读 OCR、不读游戏状态；对菜单/Boss 血量这类
需要读状态的场景无能为力。建议 plan 支持条件（每次 tick 读一次 OCR 命中即停/触发动作）。

### P2-3 「无人在场」闸的信号有洞

`engine/safety.py` 用 `GetLastInputInfo`（只统计键鼠）：
- 手柄真人玩家：3 分钟不碰键鼠会被误杀（控制器输入不计入）；
- keyboard 后端的注入键会刷新该时间戳 → agent 的注入可以给「在场」续命（自我遮蔽）；
- 本次实测离场后仍读到 `idle_seconds: 27.3, allowed: true`（当时人已离开，手柄输入不计时）。

**建议**：把 XInput 最近输入也纳入；区分「最后一次真人输入」与「最后一次注入」，注入不算在场；
审计里记录两者。

### P2-4 `game_selftest` 覆盖面不够

只报引擎就绪。建议扩展为体检表：所选后端依赖/设备、XInput 槽位、前台窗口、遮挡、审批策略、
profile 与安装来源、显示器匹配（DESIGN 已知多屏限制）。

### P2-5 双引擎/双进程没有互斥

插件引擎（宿主内，PID 39300 + 其子进程 33624）与临时驱动引擎可以同时 attach 同一窗口、各自
抓屏、各自创建虚拟手柄；没有单例锁。建议引擎加用户级单例（锁文件 + 本地端点），避免设备与状态
分裂；顺带排查「一次启动出现两个 `dsh_game_core serve` 进程」是否预期（当前 39300 的子进程 33624
命令行完全相同）。

### P2-6 引擎退出噪声

`session.close()` 后 stderr 打印 `comtypes ... OSError: exception: access violation writing 0x0`
（DXcam COM 释放）。不影响退出码，但会污染插件捕获的 stderr 尾巴（错误摘要来源），建议抑制/兜住。

### P2-7 npm 包把 README 里链接的文档排除了

README 链接 `docs/STATUS.md`，但 `package.json.files` 只有 `lib / cordis.patch.yml / README / LICENSE`
→ 装完之后用户点不开。建议把 STATUS 收进 files 或改掉链接。

### P2-8 安装期噪声

`dshmarketplace-plugin@0.2.0` 与 dsh 0.2.1-rc.2 不兼容的警告在一次安装里重复出现 3 次，
容易让人误判 game-bridge 装坏了。建议安装器去重/分组。
